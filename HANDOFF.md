# Kwik Kuote: Build and Installation Handoff

This document is for the team that receives the Kwik Kuote source package. It
covers what is in the package, how to build it, how to install it on a
workstation, how to configure it, and what still needs a decision or a test on
your side.

| | |
|---|---|
| Product | Kwik Kuote, Distributor Information System, version 3.0 |
| Origin | MS-DOS application, Borland C++ 3.1, 1994–2000 |
| This release | 64-bit build for Windows, with Linux and macOS also supported |
| Build system | CMake 3.16 or newer |
| Languages | C11 (application), C++17 (platform layer) |
| Third-party libraries | None |

For more depth, see:

* [docs/PORTING.md](docs/PORTING.md): technical design of the port and every change made to the original code.
* [docs/business-requirements-kkuote.md](docs/business-requirements-kkuote.md): the business rules the application implements.

## 1. Package contents

| Path | What it is |
|---|---|
| `CMakeLists.txt` | The build definition |
| `src/` | The application source, ported from the original |
| `src/compat/` | The platform layer, which replaces the DOS/BIOS/Borland run-time (screen, keyboard, mouse, files, printing) |
| `tools/makecfg.c`, `tools/driver.c` | Source of the two setup utilities |
| `tools/port-diff.sh` | Shows every change made to the original code (developer aid; needs the `Kk/` folder from the reference package, see below) |
| `tests/` | Automated end-to-end test (Linux/macOS only) |
| `docs/` | Technical and business documentation |

This package contains **only the new, buildable source**. The original
1994–2000 material is in the separate **reference package** delivered
earlier: the original source code (`Kk/`, `Kk_1/`, `Kk.zip`, root `*.C`/`*.H`),
the old 16-bit DOS executable `PROJKK.EXE` with its Turbo Debugger files, and
the unrelated `Web/` CGI project. None of it is needed to build. `Kk/` is the
version that `src/` was made from; the documentation mentions these folders
when it explains where the port came from.

## 2. Prerequisites

### Windows (recommended platform)

1. **Visual Studio 2022** (Community, Professional or Enterprise) or Visual
   Studio 2019, with the **"Desktop development with C++"** workload.
   This workload includes the MSVC compiler, the Windows SDK and CMake.
   *Alternative:* "Build Tools for Visual Studio 2022" (no IDE) with the same workload.
2. **CMake 3.16 or newer.** The copy bundled with Visual Studio is enough.
   To use CMake outside Visual Studio, install it from <https://cmake.org/download/>.
3. *(Optional)* **MinGW-w64** (GCC for Windows), if you prefer it to Visual Studio. See §3.3.

### Linux

```bash
sudo apt install build-essential cmake ninja-build      # Debian / Ubuntu
```
```bash
sudo dnf install gcc gcc-c++ cmake ninja-build          # Fedora / RHEL
```

GCC 9+ or Clang 10+ are expected to work. GCC 13 and Clang 18 have been tested.

### macOS

```bash
xcode-select --install
```
```bash
brew install cmake ninja
```

## 3. Building on Windows

### 3.1 From the command line (Visual Studio compiler)

Open **"x64 Native Tools Command Prompt for VS 2022"** (or "Developer
PowerShell for VS 2022") from the Start menu, go to the folder where you
extracted the package, and run:

```bat
cmake -S . -B build -G "Visual Studio 17 2022" -A x64
cmake --build build --config Release
```

For Visual Studio 2019, use `-G "Visual Studio 16 2019"`.

The outputs are written to `build\Release\`:

| File | Purpose |
|---|---|
| `kk.exe` | The Kwik Kuote application |
| `makecfg.exe` | Creates a default configuration file (`DB.CFG`) in the current folder |
| `kkdriver.exe` | Creates the default printer driver files (`DEFAULT.DRV`, `EPSON.DRV`) in the current folder |

### 3.2 Inside the Visual Studio IDE

**Option A: generated solution.** After the first command in §3.1, open
`build\KwikKuote.sln` in Visual Studio. Set the configuration to **Release /
x64** and choose **Build ▸ Build Solution**. To run from the IDE, set `kk` as
the start-up project and set its debugging **Working Directory** to a data
folder (see §5).

> The `.sln` file is generated by CMake and is not part of the package. Always
> change `CMakeLists.txt`, not the generated project files. Re-running CMake
> overwrites them.

**Option B: Open Folder.** Choose **File ▸ Open ▸ Folder…** and select the
package folder. Visual Studio detects `CMakeLists.txt`, configures the project
automatically and offers the targets `kk.exe`, `makecfg.exe` and `kkdriver.exe`.

### 3.3 With MinGW-w64 (GCC)

From a shell where `gcc`, `g++` and `cmake` are on the `PATH`:

```bat
cmake -S . -B build -G "MinGW Makefiles" -DCMAKE_BUILD_TYPE=Release -DCMAKE_EXE_LINKER_FLAGS="-static"
cmake --build build
```

The executables are written to `build\`. The `-static` flag links the GCC run-time
into the executables. Without it, `kk.exe` needs `libgcc_s_seh-1.dll` and
`libstdc++-6.dll` next to it.

### 3.4 Producing a stand-alone executable with Visual Studio

By default, MSVC builds need the **Microsoft Visual C++ Redistributable
(x64)** on every machine that runs them. Many PCs already have it. If a PC
doesn't, install it from Microsoft (search for "Visual C++ Redistributable
latest supported downloads").

To avoid that dependency, link the run-time statically:

```bat
cmake -S . -B build -G "Visual Studio 17 2022" -A x64 -DCMAKE_MSVC_RUNTIME_LIBRARY=MultiThreaded
cmake --build build --config Release
```

The resulting `kk.exe` depends only on DLLs that are part of Windows
(`KERNEL32.dll` and `USER32.dll`).

## 4. Building on Linux and macOS

```bash
cmake -S . -B build -G Ninja -DCMAKE_BUILD_TYPE=Release
```
```bash
cmake --build build
```

If Ninja is not installed, leave out `-G Ninja` and Unix Makefiles are used.
The outputs `kk`, `makecfg` and `kkdriver` are written to `build/`.

To copy the three programs into a `bin` folder under an install prefix:

```bash
cmake --install build --prefix /opt/kwikkuote
```

The same works on Windows: `cmake --install build --config Release --prefix C:\KwikKuote`.

### 4.1 Running the automated test (Linux/macOS)

```bash
python3 tests/smoke_test.py build
```

The test creates a temporary data folder and drives the real program in a
pseudo-terminal. It covers start-up, login, the menus, adding a client record,
printing, the word processor and exit, then confirms that the record is still
there on a second run. It ends with `PASS`. Python 3 is needed and nothing else.
The test does not run on Windows.

## 5. Build options

Pass options to the first (`cmake -S . -B build …`) command.

| Option | Default | Effect |
|---|---|---|
| `-DCMAKE_BUILD_TYPE=Release` / `Debug` | `Release` | Optimised or debug build (Ninja/Makefiles. With Visual Studio, use `--config` instead) |
| `-DKK_REP_VERSION=ON` | `OFF` | Builds the "Representative" variant instead of the "Distributor" variant. **Not tested.** The original code itself marks this variant as incomplete. |
| `-DKK_DEBUG_ASSERTS=ON` | `OFF` | Enables the original diagnostic assertions and error log (for troubleshooting only) |
| `-DCMAKE_MSVC_RUNTIME_LIBRARY=MultiThreaded` | – | Static MSVC run-time (see §3.4) |

## 6. Installing on a workstation

Kwik Kuote has no installer. A deployment consists of the three executables
plus a **data folder**. Like the DOS original, `kk` must be started **from
inside its data folder**. It looks for `DB.CFG` in the current directory.

### 6.1 Set up a new data folder

Example: `C:\KK` on Windows.

```bat
mkdir C:\KK
cd /d C:\KK
mkdir HELP PRODUCTS PLIST RSCH INST FAX
copy <build-folder>\Release\kk.exe        C:\KK\
copy <build-folder>\Release\makecfg.exe   C:\KK\
copy <build-folder>\Release\kkdriver.exe  C:\KK\
makecfg
kkdriver
```

* `makecfg` writes `DB.CFG` with the default company name "Automation
  Solutions, Inc." You change it later in the System Manager.
* `kkdriver` writes `DEFAULT.DRV` and `EPSON.DRV` (printer control codes).
* The data files (`AUTOMAT.CD`, `AUTOMAT.VD` and so on) are created
  automatically the first time each kind of record is saved.
* The executables don't have to live in the data folder. They can sit
  anywhere, such as `C:\Program Files\KwikKuote\` or the `PATH`, as long as `kk`
  is **started with the data folder as its working directory**.

### 6.2 Create a desktop shortcut (Windows)

Create a shortcut to `kk.exe` and set **"Start in"** to the data folder, for
example `C:\KK`. The shortcut's **Target** can include a username and password
(`kk.exe USER PASS`) to skip the login window.

### 6.3 First login and creating users

When started without arguments, `kk` shows the intro screen and then a
**Username / Password** window. A brand-new data folder has no users yet.

The original program has a **built-in master login** that works only on the
command line and is not visible in the user list:

```bat
kk iran nari
```

This login has full privileges. Use it to go to **System Manager (menu 8) ▸
USER PRIVILEGES** and create the real users, then **SYSTEM SETUP** and
**COMPANY, WAREHOUSE AND INSURANCE INFORMATION** to enter your company details.

> **Security note:** the master login is hard-coded in `src/db_sys.c` (function
> `getsec`) and works on every installation. If that is not acceptable, change
> or remove it in the source before you deploy.

### 6.4 Keyboard and screen

* The program needs a console window of at least **80 × 25** characters. On
  Windows it switches to its own 80 × 25 screen buffer and restores the
  previous one when it exits.
* It uses the function keys exactly as the DOS version did: F1 = help, F2 =
  add, F3 = delete, F5 = print, F6 = find, F10 = exit/back.
* Use a console font that has the box-drawing characters. All the standard
  Windows console fonts (Consolas, Lucida Console, Cascadia) do.
* Windows Terminal and the classic console host both work. On Linux/macOS, any
  terminal that supports ANSI colours works (xterm, GNOME Terminal, iTerm2 and so on).

### 6.5 Help files

The online help files (`HELP\DBHELP.*`) **are not in the package.** F1 shows no
help text until they are copied into the data folder's `HELP` sub-folder from
an existing installation.

## 7. Configuration

### 7.1 Printing

The DOS version wrote directly to the parallel port. This version writes each
print job to a temporary spool file, then runs a print command on it. That
happens when the job finishes, after two idle seconds, or when the program
exits. Set the command for each printer port with an environment variable.
`%s` is replaced by the spool file name.

| Variable | Used for | Windows default | Linux/macOS default |
|---|---|---|---|
| `KK_LPT1_CMD` | `LPT1` / `PRN` | `notepad /p "%s"` | `lp -s "%s"` |
| `KK_LPT2_CMD` | `LPT2` | `notepad /p "%s"` | `lp -s "%s"` |
| `KK_LPT3_CMD` | `LPT3` | `notepad /p "%s"` | `lp -s "%s"` |
| `KK_SPOOL_DIR` | Folder for spool files | `TEMP` / `TMP` | `TMPDIR` |

Examples (Windows):

```bat
rem Print to the Windows default printer through Notepad (the default):
set KK_LPT1_CMD=notepad /p "%s"
```
```bat
rem Send raw output to a shared printer:
set KK_LPT1_CMD=copy /B "%s" \\SERVER\PrinterShare
```
```bat
rem Collect output in a text file instead of printing:
set KK_LPT1_CMD=file:C:\KK\PRINTOUT.TXT
```

To make a setting permanent, use **System Properties ▸ Environment Variables**
or `setx`, or put the `set` commands in a small `.bat` file that starts `kk`.

If the print command fails, the job is appended to `LPT1.PRN` (or `LPT2.PRN`)
in the data folder and a line is written to `AUTOMAT.ERR`.

**Epson control codes:** the printer driver files that `kkdriver` creates still
contain Epson dot-matrix codes (condensed on/off). On a modern Windows printer
these may print as a few stray characters. To fix this, create a printer
driver with empty control codes in System Manager ▸ SYSTEM SETUP, or adjust
`tools/driver.c`.

### 7.2 DOS shell

**System Manager ▸ DOS SHELL** opens the host command shell (`cmd.exe` on
Windows, `$SHELL` on Linux/macOS). Type `exit` to return to Kwik Kuote.

### 7.3 E-mail

The 2000 version writes outgoing e-mail messages as files into the `FAX`
sub-folder, for an external mail program to pick up. That external program is
not part of this package.

### 7.4 Several users sharing one data folder

As in the DOS version, several workstations can run `kk` against one data folder
on a network share. Record locking uses the operating system's file locking.
This is implemented in the port but **has not been tested with several users
at once.** Test it before relying on it.

## 8. Existing data: decision required

If you are moving an existing installation onto this build, check which
version of the program wrote your data files first.

* This build is made from the **2000** source (`Kk/` in the reference package). Data written by a
  2000-era build is read as is, and no conversion is needed.
* The 2000 source **changed the record layout** of several files compared with
  1998: jobs, clients, vendors, sales people, purchase orders and discounts. For
  example, a job record grew from 395 to 489 bytes. The old `PROJKK.EXE` in the
  reference package was built from source **older than 1998**. If your production data
  was written by that executable, or by any pre-2000 build, the data files
  must be converted before this build can read them.
* A converter for the product file already exists: System Manager ▸
  CONVERSION/BACKUP/RESTORE/ARCHIVE MENU. The other files would need a small
  one-off conversion utility. It is straightforward to write once the
  production version is known.

**Always test against a copy of the production data folder, never the live one.**

could not be run in the build environment used for this handoff. A link error
specific to MSVC has already been fixed. The Windows console back end compiles

Windows:

1. Build with §3.1.
2. Set up a data folder with §6.1.
3. Start with `kk iran nari`, open **1 ▸ 1 (Client database)**, press **F2**, add

4. Press **F5** to print the record. Check that it reaches the printer, or the
   file set in `KK_LPT1_CMD`.
5. Exit with **9** then **F10**, restart, and confirm the client is still there.
6. Repeat against a **copy** of the production data (see §8).

## 10. Known limitations

* **Representative variant** (`KK_REP_VERSION`): incomplete in the original
  code and not tested.
* **Ctrl+Enter** (page break in the word processor) works on Windows but can't be
  told apart from Enter in most Linux/macOS terminals.
* **Insert key:** on Linux/macOS the Insert/Overwrite state is emulated and
  starts in overwrite mode, as the BIOS did.
* **BACKUP / RESTORE** menu entries were already disabled in the original program.
* **Not built:** `INSTALL.C` (the old floppy-disk installer), `NOTABS.C` (a
  developer tool) and `REP_RPTS.C` (duplicate reports, never linked originally).
* A few harmless bugs from the original were deliberately left unchanged,
  because fixing them would change how existing data is stored. See
  "Known, unchanged behaviour" in PORTING.md.
* Compiler warnings during the build are expected. They come from the
  1994-era C code and are not errors.

## 11. Troubleshooting

| Symptom | Cause / fix |
|---|---|
| "Error: You must run Kwik Kuote from Kwik Kuote's Main Directory", or "Can't Open CFG file" | It was not started from the data folder. Check the shortcut's **Start in**, or `cd` into the folder first. Make sure `DB.CFG` exists (run `makecfg`). |
| "Unknown User" at login on a new installation | No users exist yet. Use `kk iran nari` once and create users (§6.3). |
| Missing `VCRUNTIME140.dll` / `MSVCP140.dll` | Install the Visual C++ Redistributable (x64), or rebuild with the static run-time (§3.4). |
| Missing `libgcc_s_seh-1.dll` / `libstdc++-6.dll` | MinGW build without `-static`. Rebuild with `-DCMAKE_EXE_LINKER_FLAGS="-static"` (§3.3). |
| Garbled lines instead of boxes | The console font lacks box-drawing characters. Switch to Consolas or Cascadia Mono. |
| Screen is cut off | Enlarge the terminal to at least 80 × 25. |
| Nothing prints | Check `KK_LPT1_CMD`. Look for `LPT1.PRN` and `AUTOMAT.ERR` in the data folder. Test with `set KK_LPT1_CMD=file:C:\KK\TEST.TXT`. |
| Stray characters at the top of printouts | Epson control codes in the printer driver file (§7.1). |
| Records look corrupted or misaligned with existing data | The data was written by a pre-2000 version and needs converting (§8). |
| CMake error "Could not find any instance of Visual Studio" | Run from the "x64 Native Tools Command Prompt", or install the "Desktop development with C++" workload. |
| CMake complains about an existing `build` folder made with another generator | Delete the `build` folder and configure again. |
